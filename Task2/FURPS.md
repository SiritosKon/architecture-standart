# FURPS+ — Архитектурно-значимые требования к MVP открытия депозитов

| Код | Требования | Комментарий |
|-----|------------|-------------|
| **F** | **Функциональные (Functionality)** | |
| F1 | Отображение на сайте списка доступных депозитов с актуальными ставками | Публичная витрина: список видят все посетители без авторизации. Персональные ставки на сайте в MVP не выводим (см. F5) — они считаются по запросу и вручную. |
| F2 | Создание на сайте заявки на открытие депозита | Клиент оставляет телефон и Ф. И. О. через форму. Заявка уходит в систему кол-центра, менеджер перезванивает и может предложить особые условия. Новый клиент не идентифицирован — онлайн это только лид, не открытие депозита. |
| F3 | Авторизация пользователя в интернет-банке | Открывает доступ к персональным данным (счета, депозиты, персональные ставки). Механизм в ИБ уже есть — переиспользуем, заново не строим. |
| F4 | Личный кабинет: просмотр клиентом своих уже открытых депозитов и счетов в интернет-банке | Речь о существующих продуктах клиента (его портфель), а не о каталоге для открытия (см. F5). Допущение сверх явного задания, но без него личный кабинет неполноценен. В MVP — только чтение. |
| F5 | Витрина в интернет-банке: каталог доступных для открытия депозитов с актуальными и персональными ставками | В отличие от F4 — это продукты, которые клиент ещё может открыть. Персональная ставка считается по запросу и вручную, поэтому массово отдавать её в MVP нельзя. Максимум — кнопка «запросить персональную ставку», но и она вне MVP: пока всё обрабатывает человек, поток таких запросов будет неуправляемым. Автоматизация — на следующих этапах. |
| F6 | Создание в интернет-банке заявки на открытие депозита с указанием счёта и суммы; операция подтверждается клиентом | Подтверждение — СМС-кодом (F7). Создаётся заявка, а не сам депозит: открытие подтверждает бэк-офис (F9). |
| F7 | Отправка клиенту СМС: коды подтверждения операций и уведомления о статусе (ставка подтверждена, депозит открыт) | Единая точка работы с СМС. Функционал есть в ядре, но дорабатывать его силами подрядчика не хотим — бизнес-логику реализует команда банка поверх существующего СМС-шлюза. |
| F8 | Ведение единого справочника ставок по депозитам в АБС с доступом для сотрудников бэк-офиса депозитов и кредитов | Сейчас ставки живут только в XLS и пересылаются почтой — узкое место. Нужно вести их в едином справочнике в рамках АБС вместе с текущим процессом согласования ставки. В перспективе — основа для автоматического расчёта. |
| F9 | Обработка заявки на депозит менеджером бэк-офиса и подтверждение условий в АБС | В MVP это сознательно ручной шаг. Полную автоматизацию (открытие без участия сотрудников) выносим в целевое состояние через год. |
| **U** | **Удобство использования (Usability)** | |
| U1 | Соблюдение корпоративной дизайн-системы: привычные цвета и брендированные элементы во всех каналах | Единый визуальный язык сайта и ИБ из корпоративной дизайн-системы. |
| U2 | Соблюдение основных паттернов UI/UX в клиентских интерфейсах | Бизнес ожидает максимально удобный интерфейс. Понятная навигация и привычные формы тем важнее, что среди клиентов много людей старшего возраста. |
| **R** | **Надёжность (Reliability)** | |
| R1 | Сервисы работают 24/7 с доступностью 99,9% | Целевая планка для онлайн-каналов. Сейчас ИБ не дотягивает (один ЦОД, одна группа серверов) — требование задаёт ориентир для архитектуры. |
| R2 | Резервирование: при сбое основного ЦОД выполняется переключение на резервный ЦОД (failover) | Резервный ЦОД у банка есть, но автоматическое переключение и удержание нагрузки пока не отработаны. |
| **P** | **Производительность (Performance)** | |
| P1 | Быстрый отклик по всем клиентским операциям (миллисекунды), включая загрузку справочных данных | Сейчас справочники и большие объёмы данных грузятся долго. Новый процесс не должен это наследовать — отсюда отказ от прямых запросов к АБС (см. +5). |
| **S** | **Поддерживаемость (Supportability)** | |
| S1 | Разработка документации для дальнейшего расширения системы | Дальше систему расширяют другие команды (автооткрытие депозитов, кредиты онлайн) — без документации это не масштабируется. |
| **+** | **Ограничения (Restrictions)** | |
| +1 | Security: защита передаваемых данных шифрованием трафика (TLS) на сайте и в интернет-банке | Базовая защита: с сайта (заявки) и в ИБ (операции) идут чувствительные данные клиента. |
| +2 | Security: ролевая модель доступа для сотрудников; сотрудники депозитов и кредитов не видят данные друг друга | Прямое требование из текущего процесса согласования ставок — разделение зон ответственности. |
| +3 | Разработка на имеющемся в банке стеке (MS SQL, Oracle, Java, React); новые технологии — только совместимые с платформами и с имеющейся внутри банка экспертизой | Снижает стоимость и риски сопровождения; не плодим зоопарк технологий без поддержки. |
| +4 | Не дорабатывать ядро интернет-банка силами подрядчика; доработки (в т. ч. СМС) — силами команды банка | Обновление ядра монолита привязано к подрядчику — это узкое место по срокам и стоимости, обходим его. |
| +5 | Не нагружать БД АБС прямыми запросами интернет-банка; депозитный функционал — отдельный сервис с асинхронной интеграцией | БД АБС перегружена и масштабируется только вертикально, а ИБ требует 99,9% и роста нагрузки. Прямой поток ИБ → АБС ставит под угрозу работоспособность банка. |
| +6 | Legal: идентификация нового клиента проходит офлайн в отделении (личная проверка документов) | Регуляторное ограничение: полностью онлайн принять нового клиента нельзя. Онлайн — только заявка (лид), идентификация офлайн. |
| +7 | Очереди сообщений — Kafka на перспективу | Целевой выбор для асинхронной интеграции. Текущая платформа ИБ с Kafka несовместима — ещё один довод вынести депозиты в отдельный сервис. |
| +8 | Перевод части интернет-банка (открытие депозитов) на микросервисную архитектуру | Выносим депозиты из монолита (.NET Framework 4.5): обходим ограничения платформы, разблокируем Kafka и независимый деплой, изолируем новую нагрузку. |
